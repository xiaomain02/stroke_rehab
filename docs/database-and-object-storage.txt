БД И YANDEX OBJECT STORAGE: ДОГОВОРЁННОСТИ ДЛЯ КОМАНДЫ

1. Разделение ответственности

Участник 2: таблицы, связи, ограничения, ORM-модели, Alembic, seed.
Участник 1: проверка прав, загрузка/удаление файлов, выдача временных ссылок,
обработка ошибок и согласованность файла с записью БД.
Участники 3/4: MediaRecorder, воспроизведение, вызов API, Docker/деплой.

SQLite не подключается к Object Storage самостоятельно. SQL и внешние ключи
не могут проверить существование объекта в бакете.

2. Что хранится в media_files

uploaded_by — id авторизованного пользователя; сервер берёт его из JWT.
exercise_id — id упражнения для видео/аудиоинструкции.
attempt_id — id конкретного выполнения для ответа пациента.
Ровно одно из exercise_id и attempt_id должно быть заполнено.
media_type — audio или video.
storage_key — относительный ключ, например video/2026/10/25/<uuid>.webm.
original_name — исходное имя файла, только для отображения.
mime_type — проверенный тип файла, например video/webm.
size_bytes — фактически измеренный размер > 0.
duration_ms — длительность >= 0 или NULL, если пока неизвестна.
status — pending, ready или failed.
created_at — время создания записи.

В БД не записываются байты видео, ключи доступа S3 и presigned URL.
Уникальный storage_key предотвращает привязку одного ключа к разным строкам.
В текущей схеме бакет задаётся через S3_BUCKET для всего окружения. Если
понадобится несколько бакетов или перенос с сохранением старых объектов,
добавьте bucket отдельной миграцией, прежде чем менять этот договор.

3. Порядок загрузки через бэкенд

1) Проверить JWT и доступ к attempt/exercise. Пациент может загружать ответ
   только к своему выполнению. Инструкции загружает уполномоченный врач.
2) Проверить размер и фактический формат входного файла; не доверять только
   расширению и Content-Type браузера. Измерить размер, определить MIME,
   по возможности получить длительность. Ограничить размер/длительность.
3) Сгенерировать новый непредсказуемый storage_key. После измерения размера
   создать и закоммитить media_files со status=pending.
4) Записать объект в закрытый бакет. Синхронный boto3 вызывать через пул
   потоков из async FastAPI, чтобы не блокировать обработку других запросов.
5) Только после успешного завершения загрузки установить status=ready
   отдельной транзакцией. При ошибке — failed.
6) Если S3-загрузка прошла, а коммит ready не прошёл, нужна повторная
   сверка/очистка. Транзакция SQLite не откатывает объект в облаке.

Если объект загрузился, а ответ от S3 потерялся, перед повтором/очисткой
проверять его метаданные через HeadObject. Зависшие pending-записи и
объекты без строки БД требуют отдельной периодической сверки.

Не ставить ready на основании одного имени файла. Не создавать фиктивное
видео для seed. Не удалять старые записи/объекты автоматически при seed.

4. Получение видео и права

Клиент передаёт media_files.id, а не произвольный storage_key.
Бэкенд проверяет владельца попытки через:
media_files → attempts → assignments → doctor_patients → patient_id.
Для доступа врача проверяется его действующая связь с этим пациентом,
в том числе если назначение выдал другой врач.
Для инструкции проверяется, доступно ли упражнение данному пользователю.
Состояние файла должно быть ready.
После этого сервер генерирует временный GetObject URL. В БД остаётся только
storage_key. Подписывание URL само по себе не проверяет наличие объекта.
По истечении TTL браузер запрашивает новую ссылку у API.
Ссылку нельзя публиковать или писать целиком в логи: до истечения срока
объект доступен любому, кто её получил.

5. Что настроить в Yandex Cloud (выполняет ответственный за бэкенд/деплой)

- Создать закрытый бакет; публичное чтение объектов и списка отключить.
- Создать сервисный аккаунт и статический ключ доступа. Для S3 нужны именно
  key_id и secret статического ключа, а не IAM bearer token.
- Выдать чтение/запись объектов, а для удаления/компенсации — также удаление.
  storage.uploader позволяет читать и загружать, но не удалять объекты.
  storage.editor включает удаление, но шире по правам. Права нужно ограничить
  нужным бакетом через принятую в команде политику доступа; не выдавать admin
  на всё облако ради теста.
- В backend/.env установить S3_BUCKET, S3_ACCESS_KEY, S3_SECRET_KEY;
  endpoint https://storage.yandexcloud.net, регион ru-central1,
  SSL=true, S3_CREATE_BUCKET=false. Шаблон уже есть в .env.example.
- Фактическое имя бакета может отличаться от rehab-media: указать своё.
- Для запросов браузера напрямую к объектам настроить CORS бакета под
  конкретные origin фронтенда. Для просмотра достаточно GET/HEAD; если
  клиент отправляет Range, его нужно разрешить. Для JS можно раскрыть
  Content-Length, Content-Type, Content-Range, Accept-Ranges, ETag.
  PUT добавляется только если команда выберет прямую загрузку из браузера.
  Не добавлять OPTIONS как AllowedMethod: его обрабатывает сам сервис.
- CORS FastAPI и CORS бакета — две отдельные настройки. Они не заменяют
  авторизацию. При загрузке браузер → FastAPI → S3 браузерный CORS бакета
  не участвует в серверной записи файла.

6. Исправленная заготовка storage.py

Сигнатуры основных функций сохранены. В save_upload_stream добавлен
необязательный storage_key: это ключ, который сервер заранее зарезервировал
в pending-записи БД. Старые вызовы без этого аргумента продолжают работать.

Что исправлено:
- Вместо полного BytesIO используется временный файл с копированием блоками.
  Ограничение сервиса — 50 MiB на файл. Временные файлы очищаются при успехе
  и ошибках; исходный поток UploadFile.file остаётся открытым.
- Проверяется не только MIME: PyAV открывает заявленный контейнер и декодирует
  первый кадр. Текст и старые фиктивные WebM отклоняются до обращения к S3.
  Заявленное audio должно быть без видеопотока; video требует видеопотока.
- Парсер медиа запускается в отдельном процессе с таймаутом 15 секунд,
  запрещёнными сетевыми протоколами и ограничением размеров видеокадра.
- Разрешены video/mp4, video/webm, audio/mp4, audio/webm, audio/mpeg,
  audio/wav (также alias audio/x-wav), audio/ogg.
- MIME-параметры MediaRecorder принимаются, но для S3 используется базовый
  канонический MIME. Суффикс ключа соответствует проверенному MIME, а не
  расширению присланного имени файла.
- TTL должен быть целым числом от 1 до 3600 секунд (политика приложения),
  по умолчанию 900. Ноль, отрицательные и дробные значения отклоняются.
- Проверяются относительные ключи объектов: URL, абсолютный путь и ..
  не принимаются. Ключ генерируется с UUID без исходного имени пациента.
- Для SDK заданы таймауты подключения/чтения и ограниченное число повторов.
  403 объясняется как ошибка доступа, без попытки создать новый бакет.
- Для файлов заданы Content-Length, канонический Content-Type,
  Content-Disposition=inline и Cache-Control=private, no-store.
- Ошибки SDK преобразуются в StorageError без включения текста ответа
  провайдера. S3-ключи скрыты из repr объекта Settings.
- put_dummy() удалена: seed уже не использовал её, фиктивные файлы не нужны.

Установка после получения изменений (из backend с активным окружением):

    python -m pip install -e ".[dev]"
    python -m pytest -q

Добавленная зависимость: av>=16,<19 (PyAV). Отдельная установка ffprobe
для этого варианта не требуется. Проверка не означает декодирование всех
кадров файла, антивирусную проверку или гарантированную поддержку кодека
любым браузером. Длительность записи нужно измерить отдельно; в БД она
может пока оставаться NULL.

7. Как подключить к будущему API

Сервис синхронный: вызывать его из async FastAPI через пул потоков.
Передавать UploadFile.file, а не сам объект UploadFile. Например:

    from starlette.concurrency import run_in_threadpool
    from app.services import storage

    mime = storage.normalize_content_type("video", upload.content_type)
    reserved_key = storage.build_storage_key("video", "recording.webm")
    # Здесь сервер проверяет права, измеряет размер и сохраняет pending в БД.
    key, size = await run_in_threadpool(
        storage.save_upload_stream,
        upload.file,
        media_type="video",
        original_name=upload.filename or "recording.webm",
        content_type=mime,
        storage_key=reserved_key,
    )
    # Затем сервер меняет ту же запись БД на ready и сохраняет измеренный size.

Это пример для video/webm: reserved_key должен соответствовать фактическому
MIME. Для video/mp4 используйте имя с .mp4; для audio/mp4 — .m4a.
Ключ создаётся только сервером. Не принимайте произвольный storage_key из
запроса пациента, чтобы он не мог перезаписать чужой объект.

Задачи бэкендера остаются:
- JWT и проверка прав перед загрузкой/удалением/выдачей ссылки.
- Запись media_files и переходы pending/ready/failed, сверка с S3 при сбоях.
- Проверка размера HTTP-запроса ещё на входе в API: сервис ограничивает
  свою копию файла, но не заменяет лимит multipart на уровне HTTP.
- Обработка UploadTooLargeError как 413, обычного ValueError как ошибки
  входных данных, StorageError как ошибки конфигурации/доступности хранилища.
  UploadTooLargeError — подкласс ValueError: проверять его первым.
- Измерение длительности, при необходимости ограничения длительности.
- Интеграционный тест в реальном бакете с настоящим небольшим файлом,
  выдачей временной ссылки, воспроизведением/Range и удалением тестового файла.
- Проверка MediaRecorder.isTypeSupported() и получение финального dataavailable
  перед отправкой записи со стороны фронтенда.

После изменения ключей/настроек перезапустите процесс бэкенда: Settings
и SDK-клиент кешируются. Подписанный URL всё ещё не проверяет наличие
объекта и не проверяет права пользователя — это ответственность API.

Реальные объекты и строки media_files в этой задаче не изменялись.
main.py, docker-compose.yml, БД и краткий README не менялись.
Новые тесты используют настоящие сгенерированные клипы и подменённый S3;
запросы к реальному бакету не выполняются.
